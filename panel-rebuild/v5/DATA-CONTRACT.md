# DATA-CONTRACT - what the PC must write so the v5 launcher is never green by default (TRK-2026-9910-B)

Round 5 text, 2026-10-06 (port onto Jorge's real v3 launcher), updated in fix round 4 the same day. Same rules as the v4 contract after fix round 3, with these changes: files are named `vtes5-*.js`, there is a seventh file (`vtes5-bots.js`), the reminders bell is gone (v3 has no bell), and the status-only file is read only when `vtes5-config.js` names a folder for it. Changes against v4 are marked (V5). Fix round 4 changes are marked (R4). Fix round 5 changes are marked (R5). There is no installer, no copy command and no delete command any more: the package folder is put in place by hand in File Explorer (INSTALL-BY-HAND.md).

Rule (charter Rule 4, Tier 3 enforcement): every status, count and time on the page is READ from the files below. Nobody types a status.
If a file is missing, or its "at" is empty, the page shows **NO DATA** in red. If "at" is older than the limit, it shows **STALE since <time>** in red.
**Green appears only when the file is present AND fresh AND its content says good (R4).** A fresh file is not enough: a fresh housekeeping report that says it was not delivered is red, a fresh Miami-Dade file with no count is grey "NOT COUNTED", a fresh token report with no numbers is red NO DATA. What "says good" means is written per file below. The same verdict colours the badge in each panel and the matching entry in the status strip. **(R5) That includes the bots and heartbeat files: a fresh file is not enough. The bots entry follows the WORST bot; the heartbeat entry follows the windows it reports. Stale, impossible or out-of-range content is never green in any panel (rule 11).**
Words that ARE typed on the page (descriptions, how-to lines, the repairs log, Grok's 31-day note) are labelled "typed note" with their date, and are never green.

## Rules for time, tick and proof
1. **A time in the future is INVALID.** A file `at`, a window `last_seen`, a bot `last_run_at` or a `proof_at` more than 2 minutes ahead of the PC clock shows red **BAD CLOCK**, is never green, and its numbers are not shown.
2. **Every time on the page is Eastern, short form, with the zone** ("Oct 6, 2:05 PM EDT"). The year is added when it is not the current year. This includes the packet stamp on the first line of every hand-off packet (flaw 9 of the brief).
3. **`interval_sec` of the heartbeat file and of the bots file (the writers' own tick) must be a number from 1 to 3600.** Anything else makes that whole file red **NOT OK**. A missing `interval_sec` in the heartbeat falls back to 600 seconds (the 10-minute schedule the old status writer documents). **(R4) A single bot's own `interval_sec` (the task's repeat interval) may be a number from 1 to 604800 (7 days).** A value outside that range, or not a number, greys only that one bot ("lateness cannot be judged") and leaves the other bots and the file alone. The page and this contract now say the same thing.
   **The stale limit follows the tick: a file (and a window's `last_seen`) is STALE after 3 x `interval_sec`, never sooner than 3 minutes and never later than 3 hours.** Chat-only windows and BOTS keep their proof for 12 ticks (4 x the limit).
4. **GREEN needs proof from the poller.** A window is green only when `data\vtes5-heartbeat.js` is valid and fresh AND that window's own `executors[id].last_seen` is within 3 ticks AND its state is "up" (chat-only windows also need a fresh `proof_at`). A report that comes only from the old `vtes-status.js` shows a grey **"WRITER SAYS UP, NOT PROVEN"** and is never counted as "confirmed up".
5. **BOTS (the Grok bots)** shows UP only with `executors.BOTS.proof_at` (the moment a Grok bot finished a real task), fresh and not in the future. Otherwise the Grok card says no Grok bot has been built. It can never say both.
6. **A stale or invalid Miami-Dade file turns every proof mark neutral grey.** Only a fresh file (7 days) can show a green "proof checked".
7. **The page re-reads every data file every 60 seconds** (cache-busted) and re-evaluates every card, bot line and panel together. A file that has been deleted counts as NO DATA on the next tick.
8. **Reload swaps, it never half-empties.** Files load into NEW objects and replace the old ones only when all have answered.
9. **Only what changed is redrawn,** so a text selection survives the 60-second tick.
10. **The build time is the real build instant,** stamped by `build-v5.js` and held to rule 1 (a build time ahead of the PC clock shows red BAD CLOCK in the top line and the footer).
11. **(R5) Content that cannot be true is never green.** Per file below, a number outside the range it can have (a negative count, a percentage over 100, a count above the target of 300, more checks passed than were run), a time in the future (BAD CLOCK) and a "last report" or "report sent" time older than 26 hours (OLD) turn the badge and the strip entry red, and the number is shown in red as IMPOSSIBLE, never as a plain value.

## The seven files (V5: the bots file is new)
Each is a small JavaScript file (not JSON) so it opens from file:// with no server. Pure ASCII. In `data\` beside the launcher in the NEW v5 folder. Exactly two statements:

    window.VTES_DATA = window.VTES_DATA || {}; window.VTES_DATA.NAME = { ...fields... };

Every file has `"schema": 1`, `"at"` (ISO 8601 with offset, e.g. "2026-10-06T14:05:00-04:00") and `"writer"`. Write it atomically: write NAME.js.tmp, then rename.

1. `data\vtes5-heartbeat.js`  NAME=heartbeat  writer: the poller (a RAMBO scheduled task)  LIMIT 3 x interval_sec
   - `interval_sec` (1 to 3600): the REAL tick. The only place a "every N minutes" sentence for a window or the poller comes from.
   - `vtes_scheme_registered` (true only after VTES-Open.ps1 -Install succeeded on the PC).
   - `addresses_filled`: { "LLM-01": true|false, ... } read from vtes-addresses.json each tick. A vtes:// link appears on a card only when `vtes_scheme_registered` is true AND that window's flag is true. Otherwise the card shows one sentence saying what is missing.
   - **(R5) Says good for the strip entry:** at least one window is reported, and not every reported window is down, stale or not trusted (red when none are reported or all are unhealthy; grey "SOME DOWN" when some are; green only when none is).
   - `executors`: { "LLM-01": {"state":"up|down|unknown","last_seen":"ISO","proof_at":"ISO (chat-only windows)"}, ... } for LLM-01 to LLM-09, LOCAL, CHIEF (LLM-10 is accepted and ignored: Jorge's v3 has no Copilot card) and optionally BOTS.
2. `data\vtes5-bots.js`  NAME=bots  writer: the poller, reading the Windows scheduler (`Get-ScheduledTask`, `Get-ScheduledTaskInfo`)  LIMIT 3 x its own interval_sec (30 minutes when absent)  (V5, new)
   Fields: `interval_sec` (the writer's tick) and `bots`: { "CU-Inbox-Job-Watcher": {"state":"Ready|Running|Disabled","last_run_at":"ISO","last_result":0,"next_run_at":"ISO or null","interval_sec": n or null}, ... } for the six bots: CU-Inbox-Job-Watcher, CU-Local-Executor, CU-TokenMonitor-Hourly, CU-Orchestrator, CU-Propagation-Check, VTES-LOCAL-POLLER. `interval_sec` per bot is the task's own repeat interval from its trigger.
   What the page shows per bot: GREEN only when the bots file is fresh, the entry exists, the scheduler state is Ready or Running, `last_result` is exactly the number 0, `last_run_at` is valid, not in the future and within **1.5 x the bot's own interval (R4: a daily bot is green while its last run is inside 36 hours)**. Red: DISABLED, FAILED (any non-zero result code except the two below, shown), LATE, NO DATA (no entry, no time, no result), BAD CLOCK, STALE. **(R4) Windows result code 267009 (0x41301) means the task is RUNNING now: shown neutral blue "RUNNING NOW", never FAILED. Result code 267011 (0x41303) means the task has NOT YET RUN: shown grey "NOT YET RUN" (a missing `last_run_at` is then normal), never FAILED.** Grey: ran with result 0 but no valid `interval_sec`, so lateness cannot be judged. **(R5) Scheduler state `Queued` shows neutral blue QUEUED (never red NO DATA). A task shown as running (state Running or result code 267009) for more than 3 x its own `interval_sec` (1 hour when no valid interval is known) shows STUCK in strong grey-red: "RUNNING FOR n HOURS - CHECK" with the time it started (`last_run_at`, taken as the start of the current run); a running task with no `last_run_at` stays neutral and says how long it has run cannot be judged (RI-002: a process in the task list is not a run making progress). Says good for the strip entry (R5): all six bots (and any other bot named in the file) are fine; red when any bot is not fine (failed, late, disabled, stuck, no entry, no data), grey when none failed but some are running, queued, not yet run or unproven.** **Green here means the scheduler says the task ran and ended 0. It does not prove the task's work was right.**
3. `data\vtes5-state.js`  NAME=state  writer: the STATE-OF-PLAY exporter  LIMIT 26 hours
   Fields: `open_items`, `in_progress`, `blocked` (whole numbers of 0 or more; **(R5) anything else turns the badge and strip entry red IMPOSSIBLE**), `repairs`: [{"id","text","status":"OPEN|DONE"}], `money`: [{"item","status"}]. The `repairs` rows appear under the typed repairs log as "live rows"; if absent the page shows NO DATA there. Nobody types them.
4. `data\vtes5-health.js`  NAME=health  writer: the daily HEALTH report  LIMIT 26 hours
   Fields: `ok` (true/false, REQUIRED), `checks_passed`, `checks_total`, `panel_built_at`, `report_sent_at` (ISO or null). "says OK" = `ok` is exactly true; false shows red NOT OK; no `ok` field shows red NO DATA. **(R5) Says good also needs: `checks_total` a whole number of 1 or more and `checks_passed` a whole number from 0 to `checks_total` (otherwise red IMPOSSIBLE); `report_sent_at` valid, not in the future and inside 26 hours (otherwise red OLD or BAD CLOCK or NO DATA); and every check passed. Some failed: grey PARTIAL. None passed: red FAILING.**
5. `data\vtes5-tokens.js`  NAME=tokens  writer: the token monitor  LIMIT 30 minutes
   Fields: `burn_per_hour`, `window_used_pct` (0-100), `window_resets_at`, `week_used_pct`, `programs`: [{"name","tokens_today"}]. Do not estimate: if the monitor cannot measure, write nothing and the page says NO DATA. **(R4) Says good = `burn_per_hour` and `window_used_pct` are both numbers.** A fresh file with no numbers at all is red NO DATA; a fresh file missing one of the two is red INCOMPLETE. **(R5) A negative `burn_per_hour`, a `window_used_pct` or `week_used_pct` outside 0 to 100, or a negative `tokens_today` is red IMPOSSIBLE.**
6. `data\vtes5-housekeeping.js`  NAME=housekeeping  writer: the housekeeping agent  LIMIT 26 hours
   Fields: `last_report_at`, `report_delivered` (true/false), `delivered_to`, `items_cleaned`. **(R4) Says good = `report_delivered` is exactly true and `last_report_at` is a valid time.** delivered=false shows red NOT DELIVERED; a missing `report_delivered` shows red NO DATA. In both cases the badge and the strip entry are red, not just the line inside the panel. **(R5) `last_report_at` in the future is red BAD CLOCK; older than 26 hours is red OLD; a negative or fractional `items_cleaned` is red IMPOSSIBLE.**
7. `data\vtes5-miamidade.js`  NAME=miamidade  writer: the Miami-Dade scrape counter  LIMIT 7 days
   Fields: `counted` (n or null), `target` 300, `sources`: [{"id","name","url","proof_url","proof_ok":true|false}]. `id` is the two-digit source number as text "01" to "22" (a bare number 3 is read as "03"). Until counted the page says "unknown of 300". **(R4) Says good = `counted` is a number.** A fresh file with `counted` null or missing shows a grey "NOT COUNTED" badge (dashed grey, never green), and the strip entry is grey too. **(R5) `counted` must be a whole number from 0 to 300; 450, -3 or 7.5 is red IMPOSSIBLE and the number is not shown as a plain count.**

## What "up" means for each window
- Windows the poller can see (LLM-01 RAMBO, LLM-02 Cloud, LLM-03 Cowork, LLM-06 Codex, LLM-09 Thin API router, LOCAL, CHIEF): "up" = the poller saw the process or its own heartbeat within 3 ticks.
- Chat-only windows (LLM-04 Chat, LLM-05 iPhone, LLM-07 Grok, LLM-08 Gemini): the poller CANNOT see them. They show red NO DATA until RAMBO records a real test: `state:"up"` with `last_seen` and `proof_at` set to the moment a test message got a real reply. (V5: the v4 "site answers" mark that pinged the chat sites is NOT ported: it needed network calls, and v3's header promises no internet is needed.)

## The old status-only file (optional)
`Write-VtesStatus.ps1` writes `vtes-status.js` ("up" on a timer, checks nothing). Jorge's v3 launcher has no such file beside it. If the desktop executor wants the page to show it (as grey, never green), it edits the one line in `vtes5-config.js` so that `status_dir_url` holds that folder's `file:` address (ending in a slash). The page only reads it. VERIFY-v5.ps1 will then report `vtes5-config.js` as EDITED; that is expected and should be written in the report. Left empty, the page never looks for it.

## Shipped state
v5 ships all seven files with `"at": null`. A fresh copy shows NO DATA everywhere until the PC writes real files into `<new folder>\data\`. That is the true state, not a defect. Once a writer replaces a data file, VERIFY-v5.ps1 lists it as EDITED (data file): expected for data files, a problem for any other file.
