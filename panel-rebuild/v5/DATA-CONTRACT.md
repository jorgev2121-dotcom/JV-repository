# DATA-CONTRACT - what the PC must write so the v5 launcher is never green by default (TRK-2026-9910-B)

Round 5 text, 2026-10-06 (port onto Jorge's real v3 launcher), updated in fix round 4 the same day. Same rules as the v4 contract after fix round 3, with these changes: files are named `vtes5-*.js`, there is a seventh file (`vtes5-bots.js`), the reminders bell is gone (v3 has no bell), and the status-only file is read only when `vtes5-config.js` names a folder for it. Changes against v4 are marked (V5). Fix round 4 changes are marked (R4). Fix round 5 changes are marked (R5). Fix round 6 changes are marked (R6). There is no installer, no copy command and no delete command any more: the package folder is put in place by hand in File Explorer (INSTALL-BY-HAND.md).

Rule (charter Rule 4, Tier 3 enforcement): every status, count and time on the page is READ from the files below. Nobody types a status.
If a file is missing, or its "at" is empty, the page shows **NO DATA** in red. If "at" is older than the limit, it shows **STALE since <time>** in red.
**Green appears only when the file is present AND fresh AND its content says good (R4).** A fresh file is not enough: a fresh housekeeping report that says it was not delivered is red, a fresh Miami-Dade file with no count is grey "NOT COUNTED", a fresh token report with no numbers is red NO DATA. What "says good" means is written per file below. The same verdict colours the badge in each panel and the matching entry in the status strip. **(R5) That includes the bots and heartbeat files: a fresh file is not enough. The bots entry follows the WORST bot; the heartbeat entry follows the windows it reports. Stale, impossible or out-of-range content is never green in any panel (rule 11).**
Words that ARE typed on the page (descriptions, how-to lines, the repairs log, Grok's 31-day note) are labelled "typed note" with their date, and are never green.

## Rules for time, tick and proof
1. **A time in the future is INVALID.** A file `at`, a window `last_seen`, a bot `last_run_at` or a `proof_at` more than 2 minutes ahead of the PC clock shows red **BAD CLOCK**, is never green, and its numbers are not shown.
2. **Every time on the page is Eastern, short form, with the zone** ("Oct 6, 2:05 PM EDT"). The year is added when it is not the current year. This includes the packet stamp on the first line of every hand-off packet (flaw 9 of the brief).
3. **`interval_sec` of the heartbeat file and of the bots file (the writers' own tick) must be a number from 1 to 3600.** Anything else makes that whole file red **NOT OK**. A missing `interval_sec` in the heartbeat falls back to 600 seconds (the 10-minute schedule the old status writer documents). **(R4) A single bot's own `interval_sec` (the task's repeat interval) may be a number from 1 to 604800 (7 days).** A value outside that range, or not a number, greys only that one bot ("lateness cannot be judged") and leaves the other bots and the file alone. The page and this contract now say the same thing.
   **The stale limit follows the tick: a file (and a window's `last_seen`) is STALE after 3 x `interval_sec`, never sooner than 3 minutes and never later than 3 hours.** Chat-only windows and BOTS keep their proof for 12 ticks (4 x the limit).
4. **GREEN needs proof from the poller.** A window is green only when `data\vtes5-heartbeat.js` is valid and fresh AND that window's own `executors[id].last_seen` is within 3 ticks AND its state is "up" (chat-only windows also need a fresh `proof_at`). A report that comes only from the old `vtes-status.js` shows a grey **"WRITER SAYS UP, NOT PROVEN"** and is never counted as "confirmed up".
5. **BOTS (the Grok bots)** shows UP only with `executors.BOTS.proof_at` (the moment a Grok bot finished a real task), fresh and not in the future. Otherwise the Grok card says no Grok bot has been built. It can never say both.
6. **A stale or invalid Miami-Dade file turns every proof mark neutral grey.** Only a fresh file (7 days) can show a green "proof checked", and (R6) only for a source whose own `checked_at` is also inside 7 days.
7. **The page re-reads every data file every 60 seconds** (cache-busted) and re-evaluates every card, bot line and panel together. A file that has been deleted counts as NO DATA on the next tick.
8. **Reload swaps, it never half-empties.** Files load into NEW objects and replace the old ones only when all have answered.
9. **Only what changed is redrawn,** so a text selection survives the 60-second tick.
10. **The build time is the real build instant,** stamped by `build-v5.js` and held to rule 1 (a build time ahead of the PC clock shows red BAD CLOCK in the top line and the footer).
11. **(R5) Content that cannot be true is never green.** Per file below, a number outside the range it can have (a negative count, a percentage over 100, a count above the target of 300, more checks passed than were run), a time in the future (BAD CLOCK) and a "last report" or "report sent" time older than 26 hours (OLD) turn the badge and the strip entry red, and the number is shown in red as IMPOSSIBLE, never as a plain value.

12. **(R6) One colour function, one enforcement pass (charter Rule 4, Tier 2 and Tier 3).** A state word becomes a colour in ONE function (`clsOfState` in vtes5-live.js). After every paint, ONE function (`enforce` in vtes5-ui.js) reads the page itself: every state line (window card, role card, bot line, the LOCAL save line) and every mark inside a panel names the data file(s) it uses, and each badge and each strip entry for a file is raised to the WORST of those items. The line **WHOLE PAGE** is the worst of everything. So no strip entry, badge or summary can be greener than a card or a mark printed on the same page, whatever a verdict says. A window that is missing from the heartbeat file is NO DATA (red) and so is its card; the heartbeat entry follows the cards, not a count made by a second piece of code.
13. **(R6) One freshness rule for every date shown as a value.** `dateJudge` in vtes5-live.js. A per-item date (report sent, last report, proof checked, local-folder check) older than its limit is red OLD, in the future is red BAD CLOCK, missing is red NO DATA. A due or reset time (the token window reset) that is already in the past is red PAST. Such a date is never shown plain and never green, and the numbers beside a PAST reset time are called out as belonging to a finished window.
14. **(R6) Numbers from a file that is not fresh are never plain.** If the state, health, housekeeping or token file is STALE, every number printed from it is a red mark `OLD n` and the panel says "These numbers are old. Do not trust them." (the token panel already did; the state, health, housekeeping and live repair panels now do too).
15. **(R6) A scheduler state that is waiting for a time is not good news forever.** `Running`, `Queued` and `Running with no start time` all time out the same way: after the LARGER of 3 x the task's own interval and 1 hour (1 hour when no valid interval is known) the bot line turns red **STUCK - CHECK**. The time counted from is: the start of the run (Running with `last_run_at`), the scheduler's last-run time (Queued with `last_run_at`), or, when the report gives no time at all, the moment THIS page first saw that state (kept in memory only; a reload of the page restarts the count). Result code 267010 (0x41302) is the scheduler's "task disabled" code and is worded **DISABLED - the scheduler says this task is turned off**, not FAILED.

## The seven files (V5: the bots file is new)
Each is a small JavaScript file (not JSON) so it opens from file:// with no server. Pure ASCII. In `data\` beside the launcher in the NEW v5 folder. Exactly two statements:

    window.VTES_DATA = window.VTES_DATA || {}; window.VTES_DATA.NAME = { ...fields... };

Every file has `"schema": 1`, `"at"` (ISO 8601 with offset, e.g. "2026-10-06T14:05:00-04:00") and `"writer"`. Write it atomically: write NAME.js.tmp, then rename.

1. `data\vtes5-heartbeat.js`  NAME=heartbeat  writer: the poller (a RAMBO scheduled task)  LIMIT 3 x interval_sec
   - `interval_sec` (1 to 3600): the REAL tick. The only place a "every N minutes" sentence for a window or the poller comes from.
   - `vtes_scheme_registered` (true only after VTES-Open.ps1 -Install succeeded on the PC).
   - `addresses_filled`: { "LLM-01": true|false, ... } read from vtes-addresses.json each tick. A vtes:// link appears on a card only when `vtes_scheme_registered` is true AND that window's flag is true. Otherwise the card shows one sentence saying what is missing.
   - **(R6) Says good for the strip entry:** the file is fresh AND lists at least one window AND every window and role card on the page that uses it is green (rule 12). One red card makes the heartbeat entry red. A window the file does not list is NO DATA: red. (R5 had grey "SOME DOWN" and counted only DOWN or STALE windows as unhealthy; that let green sit above 15 red cards. Removed.)
   - **(R6) `local_only_folder`** (new, optional): `{ "ok": true, "checked_at": "ISO", "label": "C:\\VTES-LOCAL-ONLY", "local_only_verified_by": "who checked", "not_synced_proof": "one sentence: how it was checked that the folder is not synced" }` (round 7: the last two fields are new). Written by RAMBO only after it has CREATED or CONFIRMED, with its own file tools, a folder that is NOT inside Google Drive, OneDrive, Dropbox, iCloud or any other syncing folder. Until it says `ok: true` with a `checked_at` inside 26 hours and a `label` that passes the round-7 ALLOW rule (the label must be a plain `C:\` path that is NOT under `Users\<name>\Desktop`, `OneDrive` or `Documents`; OR RAMBO also writes both `local_only_verified_by` and `not_synced_proof`; labels with `G:\`, "Shared drives", "My Drive", "Google Drive", "Desktop", "Documents", "OneDrive", "Dropbox", "iCloud", "Box Sync" or "sync" are ALWAYS refused, proof or not), the LOCAL card says **BLOCKED - UNVERIFIED** in red and gives no save instructions. The page cannot see the folder; it shows what the PC reports.
   - `executors`: { "LLM-01": {"state":"up|down|unknown","last_seen":"ISO","proof_at":"ISO (chat-only windows)"}, ... } for LLM-01 to LLM-09, LOCAL, CHIEF (LLM-10 is accepted and ignored: Jorge's v3 has no Copilot card) and optionally BOTS.
2. `data\vtes5-bots.js`  NAME=bots  writer: the poller, reading the Windows scheduler (`Get-ScheduledTask`, `Get-ScheduledTaskInfo`)  LIMIT 3 x its own interval_sec (30 minutes when absent)  (V5, new)
   Fields: `interval_sec` (the writer's tick) and `bots`: { "CU-Inbox-Job-Watcher": {"state":"Ready|Running|Disabled","last_run_at":"ISO","last_result":0,"next_run_at":"ISO or null","interval_sec": n or null}, ... } for the six bots: CU-Inbox-Job-Watcher, CU-Local-Executor, CU-TokenMonitor-Hourly, CU-Orchestrator, CU-Propagation-Check, VTES-LOCAL-POLLER. `interval_sec` per bot is the task's own repeat interval from its trigger.
   What the page shows per bot: GREEN only when the bots file is fresh, the entry exists, the scheduler state is Ready or Running, `last_result` is exactly the number 0, `last_run_at` is valid, not in the future and within **1.5 x the bot's own interval (R4: a daily bot is green while its last run is inside 36 hours)**. Red: DISABLED, FAILED (any non-zero result code except the two below, shown), LATE, NO DATA (no entry, no time, no result), BAD CLOCK, STALE. **(R4) Windows result code 267009 (0x41301) means the task is RUNNING now: shown neutral blue "RUNNING NOW", never FAILED. Result code 267011 (0x41303) means the task has NOT YET RUN: shown grey "NOT YET RUN" (a missing `last_run_at` is then normal), never FAILED.** Grey: ran with result 0 but no valid `interval_sec`, so lateness cannot be judged. **(R5, changed in R6: see rule 15) Scheduler state `Queued` shows neutral blue QUEUED at first. A task shown as running (state Running or result code 267009) or queued longer than the LARGER of 3 x its own `interval_sec` and 1 hour (1 hour when no valid interval is known) shows STUCK in strong grey-red: "RUNNING FOR n HOURS - CHECK" (running, with the start time `last_run_at`) or "STUCK - CHECK. QUEUED for ..." / "STUCK - CHECK. RUNNING for ..." (queued, or running with no start time; counted from the last-run time or, if there is none, from when the page first saw the state). Result code 267010 is worded DISABLED, not FAILED (RI-002: a process in the task list is not a run making progress). Says good for the strip entry (R5): all six bots (and any other bot named in the file) are fine; red when any bot is not fine (failed, late, disabled, stuck, no entry, no data), grey when none failed but some are running, queued, not yet run or unproven.** **Green here means the scheduler says the task ran and ended 0. It does not prove the task's work was right.**
3. `data\vtes5-state.js`  NAME=state  writer: the STATE-OF-PLAY exporter  LIMIT 26 hours
   Fields: `open_items`, `in_progress`, `blocked` (whole numbers of 0 or more; **(R5) anything else turns the badge and strip entry red IMPOSSIBLE**), `repairs`: [{"id","text","status":"OPEN|DONE"}], `money`: [{"item","status"}]. The `repairs` rows appear under the typed repairs log as "live rows"; if absent the page shows NO DATA there. Nobody types them. **(R6) When this file is STALE (older than 26 hours) its numbers, its money list and its repair rows are shown as red `OLD` marks with the sentence "These numbers are old. Do not trust them." (rule 14).**
4. `data\vtes5-health.js`  NAME=health  writer: the daily HEALTH report  LIMIT 26 hours
   Fields: `ok` (true/false, REQUIRED), `checks_passed`, `checks_total`, `panel_built_at`, `report_sent_at` (ISO or null). "says OK" = `ok` is exactly true; false shows red NOT OK; no `ok` field shows red NO DATA. **(R5) Says good also needs: `checks_total` a whole number of 1 or more and `checks_passed` a whole number from 0 to `checks_total` (otherwise red IMPOSSIBLE); `report_sent_at` valid, not in the future and inside 26 hours (otherwise red OLD or BAD CLOCK or NO DATA); and every check passed. Some failed: grey PARTIAL. None passed: red FAILING.**
5. `data\vtes5-tokens.js`  NAME=tokens  writer: the token monitor  LIMIT 30 minutes
   Fields: `burn_per_hour`, `window_used_pct` (0-100), `window_resets_at`, `week_used_pct`, `programs`: [{"name","tokens_today"}]. Do not estimate: if the monitor cannot measure, write nothing and the page says NO DATA. **(R4) Says good = `burn_per_hour` and `window_used_pct` are both numbers.** A fresh file with no numbers at all is red NO DATA; a fresh file missing one of the two is red INCOMPLETE. **(R5) A negative `burn_per_hour`, a `window_used_pct` or `week_used_pct` outside 0 to 100, or a negative `tokens_today` is red IMPOSSIBLE.** **(R6) `window_resets_at` is REQUIRED for green and must still be in the future: a reset time that has already passed (or is missing) is red PAST (or NO DATA / INCOMPLETE) on the badge, the strip and the panel, because the numbers belong to a finished window (rule 13).**
6. `data\vtes5-housekeeping.js`  NAME=housekeeping  writer: the housekeeping agent  LIMIT 26 hours
   Fields: `last_report_at`, `report_delivered` (true/false), `delivered_to`, `items_cleaned`. **(R4) Says good = `report_delivered` is exactly true and `last_report_at` is a valid time.** delivered=false shows red NOT DELIVERED; a missing `report_delivered` shows red NO DATA. In both cases the badge and the strip entry are red, not just the line inside the panel. **(R5) `last_report_at` in the future is red BAD CLOCK; older than 26 hours is red OLD; a negative or fractional `items_cleaned` is red IMPOSSIBLE.**
7. `data\vtes5-miamidade.js`  NAME=miamidade  writer: the Miami-Dade scrape counter  LIMIT 7 days
   Fields: `counted` (n or null), `target` 300, `sources`: [{"id","name","url","proof_url","proof_ok":true|false,"checked_at":"ISO"}]. **(R6) `checked_at` is the moment the PC last re-checked that one source's proof. A source is green "proof checked" only when `proof_ok` is exactly true AND `checked_at` is a valid time, not in the future, and within 7 days. `proof_ok` true with no `checked_at` is grey "PROOF OK BUT NO CHECK DATE: not counted as checked". `checked_at` older than 7 days is red "PROOF OLD"; in the future is red BAD CLOCK; `proof_ok` not true is red PROOF NOT OK; a source missing from a fresh file is red NOT RE-CHECKED. The strip entry is never greener than the worst source row.** `id` is the two-digit source number as text "01" to "22" (a bare number 3 is read as "03"). Until counted the page says "unknown of 300". **(R4) Says good = `counted` is a number.** A fresh file with `counted` null or missing shows a grey "NOT COUNTED" badge (dashed grey, never green), and the strip entry is grey too. **(R5) `counted` must be a whole number from 0 to 300; 450, -3 or 7.5 is red IMPOSSIBLE and the number is not shown as a plain count.**

## What "up" means for each window
- Windows the poller can see (LLM-01 RAMBO, LLM-02 Cloud, LLM-03 Cowork, LLM-06 Codex, LLM-09 Thin API router, LOCAL, CHIEF): "up" = the poller saw the process or its own heartbeat within 3 ticks.
- Chat-only windows (LLM-04 Chat, LLM-05 iPhone, LLM-07 Grok, LLM-08 Gemini): the poller CANNOT see them. They show red NO DATA until RAMBO records a real test: `state:"up"` with `last_seen` and `proof_at` set to the moment a test message got a real reply. (V5: the v4 "site answers" mark that pinged the chat sites is NOT ported: it needed network calls, and v3's header promises no internet is needed.)

## The old status-only file (optional)
`Write-VtesStatus.ps1` writes `vtes-status.js` ("up" on a timer, checks nothing). Jorge's v3 launcher has no such file beside it. If the desktop executor wants the page to show it (as grey, never green), it edits the one line in `vtes5-config.js` so that `status_dir_url` holds that folder's `file:` address (ending in a slash). ## Files that change by design (R6, exactly eight)
These are the ONLY files in the package a PC writer is expected to rewrite. On day one VERIFY-v5.ps1 is exact: a change to any file, these eight included, is PROBLEMS (exit 1). Run with `-AfterWriters`, a changed one of these eight is accepted (exit 0) ONLY if it passes the strict shape check, and is printed as `changed by a PC writer (passes the strict shape check)`. A change to ANY other package file is always PROBLEMS.

**The exact shape every writer must produce (round 7):** (1) UTF-8, no byte-order mark. (2) LF line endings only, no CR anywhere. (3) Exactly `window.VTES_DATA = window.VTES_DATA || {}; window.VTES_DATA.<name> = ` then ONE JSON object, then `;`, then at most one LF; `<name>` is the file's own name (`vtes5-bots.js` assigns `.bots`). The settings file is `window.VTES5_CONFIG = ` + ONE JSON object + `;` (`status_dir_url` a text string; one optional first line that is a single closed /* comment */). (4) At most 1048576 bytes. (5) Never save from a Windows PowerShell 5.1 redirect: it writes UTF-16 and VERIFY refuses it. (6) The page reads each file through ONE sanitiser: a list written as one object becomes a one-item list; an empty or wrong-type entry is dropped and counted, and the file then shows red UNREADABLE; unknown keys are ignored; text over 1000 characters is cut; lists over 500 entries and maps over 200 keys are cut. Write what the contract says and none of this ever triggers.

A data file that is missing, a link, unreadable, or an extra file anywhere in the folder is still a problem. The list is written in VERIFY-v5.ps1 and here; INSTALL-BY-HAND.md and DESKTOP-WORK.md say the same eight.

## Shipped state
v5 ships all seven files with `"at": null`. A fresh copy shows NO DATA everywhere until the PC writes real files into `<new folder>\data\`. That is the true state, not a defect. Once a writer replaces a data file, VERIFY-v5.ps1 run with `-AfterWriters` lists it as `changed by a PC writer (passes the strict shape check)` and answers OK; without the switch it is EDITED. Any other file that differs is PROBLEMS.
