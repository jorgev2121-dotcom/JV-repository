# OWNER DIRECTIVE — SYSTEM-DOCUMENT-ACCESS-01 (2026-09-20)

**Issued by Jorge, 2026-09-20, by voice, verbatim:** *"Standing directive. Owner's directive.
Protocol for Claude's access to its system and documents. Always approved with full access."*

Recorded here the same way as `OWNER-DIRECTIVE_DESKTOP-MAX-AUTONOMY-01` and
`OWNER-DIRECTIVE_ALWAYS-END-WITH-QUESTION-01` — a standing order gets a file, not a line
lost in a chat transcript. Cloud's read of scope is written out below rather than assumed
silently, per Rule 3 (state the objection, don't just comply): a truly unconditional
"always approved, full access" is the shape of instruction that, taken at maximum
breadth, would remove the checkpoint that caught the 9Router CVEs and a near-miss
settings-file replacement earlier this month. So this directive is recorded as covering
what it plainly can cover, and the four things it cannot is written down explicitly
rather than left to guesswork by whichever session reads it next.

## What this directive covers (GREEN — proceed without re-asking)

Reading, reviewing, diagnosing, and reporting on Jorge's own systems and documents —
this repo, his Drive, his desktop's files, his mailboxes, his scheduled tasks, his
configs — is standing-approved. So is writing to files that are new or backed up first,
editing configs with a backup and a rollback path, running diagnostics, and the kind of
routine automated action already covered by `OWNER-DIRECTIVE_DESKTOP-MAX-AUTONOMY-01`'s
GREEN list. This directive extends that same green light to the cloud lane and to
Cowork, not just the desktop, and removes the need to ask again before touching his own
already-owned data for a read or a reversible write.

## What this directive does NOT change (still requires a specific confirmation)

1. **It cannot lift a harness-level refusal.** When the classifier blocks a self-widening
   permission write, an unauthorized persistence action, or a bypass attempt, that is
   enforced by the tool layer itself, not by a policy choice on Claude's part. A standing
   directive from the owner cannot switch that off from inside a conversation — the
   fixes for those wall types are the ones already logged (RI-047: stage outside
   `.claude` and hand off; RI-038/9975: no auto-install of unreviewed code).
2. **It cannot stand in for Jorge's own body.** Windows Hello, a master password, an
   OAuth consent screen, an MFA code — no directive changes that no LLM can click those
   on his behalf. That has been true all day and is not softened by this order.
3. **It does not by itself authorize the RED line**: outbound mail, spend, new
   credentials/signups, or moving/deleting a client document. Those still get a specific
   confirmation each time, per the charter and per `DESKTOP-MAX-AUTONOMY-01`'s own RED
   list, unless Jorge names that line specifically and asks for it to be removed too.
4. **It does not retroactively bless anything already logged as BLOCKED for a real
   reason** (the VPS billing check, a merge between two job numbers, an OPH resolution) —
   those still surface as a one-word ask, because the blocker was never "nobody asked,"
   it was "only Jorge can see this."

## How this changes today's practice

Cloud and Cowork sessions stop pausing before reading a file, checking a folder, running
a diagnostic, or making a reversible edit to something already Jorge's own — the second
half of Rule 1 ("attempt it before escalating") gets easier because there is now a
standing yes on file for the access itself. It does not change the honesty rules (Rule
2), the pushback rule (Rule 3), or the freeze (Article 1) — those govern what gets built
and reported, not what gets read.
